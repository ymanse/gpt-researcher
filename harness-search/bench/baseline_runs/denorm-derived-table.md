# Best-Practice Design for an Asynchronously Rebuilt Denormalized Tree Table (ORDERINDEX / DEPTH / ancestor-path / subtree counts)

## Problem framing

The design under review is a classic *materialized view implemented as a plain table*: a derived table holding nested-set-style tree ordering (ORDERINDEX), DEPTH, an ancestor path, and subtree aggregate counts, rebuilt asynchronously when a cross-process notification arrives, while read APIs INNER JOIN it against the base entity table. This is exactly the shape PostgreSQL's materialized view machinery formalizes: a refresh "completely replaces the contents of a materialized view" and, unless refreshed `CONCURRENTLY`, "could block other connections which are trying to read from the materialized view" [1] ("REFRESH MATERIALIZED VIEW completely replaces the contents of a materialized view"). The four failure axes below — silent truncation, read consistency, rebuild cost, and authorization derivation — are all consequences of the derived table lagging its base tables.

## 1. Avoiding silent truncation when the read path INNER JOINs a lagging derived table

An INNER JOIN between the base table and a derived table that has not yet absorbed the latest inserts silently drops the new base rows: the API returns fewer rows than exist, with no error. Three defensible designs exist, and database engines themselves have taken positions:

**Fail-loud (preferred for correctness-critical reads).** PostgreSQL's own design is fail-loud for the analogous case: a materialized view refreshed `WITH NO DATA` is "left in an unscannable state" [1] ("the materialized view is left in an unscannable state") — querying an unpopulated view raises an error rather than returning an empty (and therefore wrong) result. Tellingly, the pg_ivm maintainers treat silently-empty scans of an unpopulated incrementally-maintained view as a defect to be fixed: "unpopulated IMMV is still scannable although the result is empty. This behaviour may be changed in future to raise an error when an unpopulated IMMV is scanned" [7]. The application-level equivalent for a derived tree table is a cheap validity check on the read path: compare a version/watermark column (or `count(*)` reconciliation for the tenant/subtree in question) and return an explicit 503/"index rebuilding" error or trigger sync-on-read, instead of returning a truncated list. Silent under-reporting is worse than a visible failure because downstream consumers (UI totals, permission scopes, billing) treat the short list as the whole truth.

**LEFT JOIN with explicit "unindexed" semantics.** Where availability matters more than completeness of derived attributes, LEFT JOIN the derived table and COALESCE the derived columns (DEPTH, ORDERINDEX, counts) to sentinel values, so base rows never disappear — they merely render unsorted/uncounted and can be flagged in the payload. This converts silent truncation into visible degradation. The cost is that every consumer must handle NULL derived columns; it is the right trade only when the derived columns are decoration (ordering, counts) rather than a filter predicate.

**Read-your-writes barrier (see §2).** Block or redirect the read until the derived table's watermark is at least as fresh as the client's last write. This is the strongest option and the only one that makes "create node, then immediately list children" behave correctly.

What is *not* defensible is the status quo: INNER JOIN with no freshness signal. Even vendors of refresh tooling warn that "materialized views can become stale between refresh intervals, leading to outdated results" [14] — staleness is expected; *undetected* staleness combined with an INNER JOIN is the bug.

## 2. Read-your-writes and monotonic reads for asynchronously maintained derived tables

Kleppmann's replication-lag taxonomy maps directly onto an async-rebuilt derived table (the derived table plays the role of an asynchronous follower). Two anomalies matter:

- **Read-your-writes violation:** "If a client writes a value to a leader and tries to read that same value, the read request might go to an asynchronous follower that has not received the write yet as a result of replication lag" [3]. Kleppmann's standard remedies translate directly: (a) route reads that could reflect the user's own writes to the authoritative source — "read it from the leader, else read it from a follower" [3]; i.e., after a tree mutation, serve that session's next tree read from a recursive CTE over the base table (or synchronously refresh just that subtree) instead of the derived table; (b) token-based barriers — "keep track of the time of the update, and only read from followers whose last updated time is at least that. The timestamp could be a logical one, like a sequence of writes" [3]. Concretely: the writer records a monotonically increasing version (LSN, sequence, or mutation counter) at commit; the rebuild process stamps the derived table with the version it has absorbed; the read API compares the session's write-version against the derived table's watermark and either waits, falls back, or fails loud.
- **Monotonic reads violation:** with multiple rebuild targets or replicas a user can see the tree "moving backward in time"; the guarantee "that a user will not read older data after having previously read newer data" is obtained by making "every read from a user ... go to the same replica" [3] — or, in single-database form, by never *replacing* the derived table with an older snapshot (rebuilds must be serialized and versions must only advance).

**The production-grade version of the watermark token is Google Zanzibar's zookie.** Zanzibar provides "external consistency and snapshot reads with bounded staleness" [5]; "a Zanzibar client requests an opaque consistency token called a *zookie* for each content version ... when the content modification is about to be saved" and "the client sends this zookie in subsequent ACL check requests to ensure that the check snapshot is at least as fresh as the timestamp for the content version" [5]. The zookie's "at-least-as-fresh semantics ... allow Zanzibar to choose any timestamp fresher than the one encoded in a zookie" [5], which is exactly the right contract for a derived tree table: the client does not demand *latest*, only *not older than my write*. In the paper's terms, "zookies in ACL read and check requests specify stateless bounds for snapshot reads" [6].

**Making the cross-process notification reliable: the transactional outbox.** A fire-and-forget notification from the writing process to the rebuilder is a dual-write and can be lost ("if a service sends a message after committing the transaction there's no guarantee that it won't crash before sending the message" [4]). The outbox pattern fixes this: "the service that sends the message ... first store[s] the message in the database as part of the transaction that updates the business entities. A separate process then sends the messages" [4], with the guarantee that "messages are guaranteed to be sent if and only if the database transaction commits" [4]. Because "the Message relay might publish a message more than once ... a message consumer must be idempotent" [4] — which a rebuild naturally is, provided rebuilds are serialized. A lighter-weight in-database variant is PostgreSQL LISTEN/NOTIFY driving `REFRESH MATERIALIZED VIEW CONCURRENTLY` from a trigger, with the caveat that "even with CONCURRENTLY, one REFRESH still blocks another one, so any INSERT/UPDATE/DELETE on the involved tables will be serialized" [2] — PostgreSQL itself enforces that "only one REFRESH at a time may run against any one materialized view" [1].

**Write-through vs write-behind.** pg_ivm's terminology is the cleanest statement of the choice: "In immediate maintenance, views are updated in the same transaction that its base table is modified. In deferred maintenance, views are updated after the transaction is committed, for example, when the view is accessed, ... or periodically in background" [7]. Immediate (write-through) maintenance gives read-your-writes for free but taxes every mutation; deferred (write-behind, the design under review) needs the watermark/barrier machinery above plus an explicit staleness bound and staleness monitoring — Kleppmann notes systems should "monitor whether databases are returning up-to-date results, even if the application can tolerate stale reads ... If a replica falls behind significantly, the database should alert you" [3].

## 3. Incremental maintenance of nested-set / tree ordering instead of full O(n) rebuilds

A full rebuild per mutation is the `REFRESH MATERIALIZED VIEW` model: "recomputing the contents from scratch"; incremental maintenance "computes and applies only incremental changes ... more efficiently than recomputation when only small parts of the view are changed" [7]. For tree encodings specifically, the literature disagrees on the best structure, and the honest answer is workload-dependent:

- **Nested sets** are the read-optimized extreme: "Very fast queries for deep trees. No recursion needed" but "Complex inserts and updates" [8] — a single insert renumbers left/right values for, on average, half the table, which is why per-mutation full rebuilds feel natural (and are the O(n) trap). Nested sets are the right choice only for read-mostly trees rebuilt in batches.
- **Closure tables** store every ancestor–descendant pair with depth; they give "Fast queries for deep hierarchies" and are "Very flexible", at the cost that "Inserts and deletions involve multiple updates" and "More storage [is] required" [8]. Critics note the storage ceiling: "the closure table comes with real tradeoffs: Storage can blow up to O(n²) in the worst case" [13] (degenerate deep chains). A closure table is incrementally maintainable per-mutation (insert = copy parent's ancestor rows + self-row; move subtree = delete/reinsert the cross-product for that subtree only), which makes it the standard recommendation for write-heavy deep trees.
- **Materialized paths** (your ancestor-path column; SQL Server's `hierarchyid` is the productized form) are "Simple to implement, Fast reads using string pattern matching" but "Updates require rewriting affected paths" [8]. `hierarchyid` demonstrates that path encodings support cheap local edits: "it's always possible to generate a sibling to the right of any given node, to the left of any given node, or between any two siblings", and "comparison is in depth-first order" so a depth-first index makes subtree scans a range seek [9]. Microsoft also quantifies the subtree-move cost precisely: "Changing the location of a row in a hierarchyid usage affects *n* rows, where *n* is number of nodes in the subtree being moved" [9] — i.e., O(subtree), not O(tree), and their documented `MoveOrg` pattern does it in one `UPDATE ... GetReparentedValue ...` inside a serializable transaction [9].
- **Interval / gap-based ordering (fractional indexing)** eliminates renumbering for ORDERINDEX-style sibling ordering. Figma's approach: "Every object has a real number as an index ... To insert between two objects, just set the index for the new object to the average index of the two objects on either side. We use arbitrary-precision fractions instead of 64-bit doubles so that we can't run out of precision after lots of edits" [10], with the acknowledged drawback that "index length can grow over time" [10]. Combined with a materialized path or closure table, fractional sibling keys give a global depth-first sort key with O(1) writes for insert/reorder — replacing the dense ORDERINDEX that forces renumbering.

**Subtree aggregate counts** are the aggregate-view sub-problem: pg_ivm maintains `count`/`sum` incrementally via AFTER triggers, but warns that concurrent maintenance requires locking ("ExclusiveLock is held on an IMMV immediately after a base table is modified" [7]); an application-level equivalent is incrementing ancestor counters along the (short) ancestor path per mutation rather than recounting subtrees.

**Bulk imports must coalesce, not iterate.** Two authoritative patterns: (a) *disable-then-rebuild-once* — pg_ivm's documented escape hatch for exactly this case: "when a large part of a base table is modified or large data is inserted into a base table, IVM is not effective and the cost of maintenance can be larger than refresh from scratch. In such situation, we can use refresh_immv ... with_data = false to disable immediate maintenance before modifying a base table" and re-enable/refresh once afterwards [7]. Applying per-row incremental tree maintenance (or worse, per-row full rebuilds) during an N-row import is how O(n²) re-enters. (b) *debounce/coalesce notifications* — when many refresh requests queue up, "only the latest query is of any relevance; all the previous queries consume processing time in vain to refresh stale data" [15]; the rebuilder should therefore drain its notification queue and run one rebuild per burst (a dirty-flag + single worker, not one rebuild per NOTIFY). Because refreshes on one view are serialized anyway [1][2], the coalescing must happen *before* the queue, or imports simply convert into a backlog of redundant sequential rebuilds.

## 4. Deriving authorization scope from these reads: fail-closed, and representing "all" vs "none"

If the permission scope list (e.g., the set of subtree roots a user may see) is computed by joining against the lagging derived table, the truncation failure of §1 becomes a security property. The direction of the failure decides whether it is an outage or a breach — and the guidance is unanimous that it must fail toward *deny*:

- OWASP Authorization Cheat Sheet: "Even when no access control rules are explicitly matched, the application cannot remain neutral when an entity is requesting access to a particular resource. ... For security purposes an application should be configured to deny access by default" [11]; and on failure handling, "developers must plan for such failures and handle them securely", ensuring failures "do not put the software into an unstable state that could lead to authorization bypass" [11].
- OWASP Developer Guide (fail-safe defaults): "unless an entity is given explicit access to an object, it should be denied access to that object by default. This is often described as 'Fail Safe'" [12].

The concrete anti-pattern: a filter builder that interprets an *empty* scope list as "no filter" (unrestricted). Then any lag, rebuild race, or bug that yields an empty list silently grants global access — fail-open. Under deny-by-default, empty must mean *deny everything* (e.g., generate `WHERE 1=0`, or short-circuit with an empty API result), and the *inability to compute* the scope (derived table unscannable/stale beyond bound) must be an error, not an empty list.

That forces the standard representational rule: **"all" and "none" must be distinct, explicit states, never both encoded as an empty collection.** Use a tagged type — `Unrestricted` vs `Restricted(set)` with `Restricted(∅) = deny` — or an explicit `is_unrestricted` flag alongside the set; "one should be able to explicitly justify why a specific permission was granted" [11], which an implicit empty-means-all encoding makes impossible to audit. Zanzibar shows why the *freshness* of the permission read is itself security-relevant: evaluating checks against stale ACL data creates the "'new enemy' problem, which can arise when we fail to respect the ordering between ACL updates or when we apply old ACLs to new content" [5]. Its mitigation — carry a consistency token with the protected content and require the permission evaluation snapshot to be "at least as fresh" as that token [5] — is precisely the §2 watermark barrier applied to the authorization path. A revoked-access example: if a user's subtree access is revoked in the base tables but the derived scope table lags, an inner join against the stale scope table keeps granting access until the rebuild lands; the zookie-style bound turns that window into a bounded, auditable staleness instead of an open-ended one.

## Recommended composite design

1. Add a monotonic `rebuild_version` watermark to the derived table; writers capture their commit version; reads compare and choose: wait briefly, sync-on-read for the affected subtree, or fail loud — never INNER JOIN blind [1][3][5].
2. Replace the ad-hoc cross-process notification with an outbox row written in the mutating transaction, drained by one idempotent rebuild worker that coalesces bursts into a single rebuild [4][15].
3. Replace the full-rebuild encoding: closure table (write-heavy, deep trees) or materialized path/hierarchyid-style keys with fractional sibling ordering (read-heavy with drag-reorder), maintaining counts by ancestor-path increments; keep full rebuild only as the bulk-import path, executed once per import with incremental maintenance disabled [7][8][9][10][13].
4. Make the permission-scope reader fail-closed: distinct `Unrestricted` / `Restricted(set)` types, `Restricted(∅)` = deny, scope-computation failure = request failure, and (ideally) a zookie-style freshness bound on authorization reads [5][11][12].
