# Practical Failure Modes of Transactional Outbox Pattern Implementations in Production

## Why the pattern exists — and why it still fails

The transactional outbox pattern is the canonical answer to the dual-write problem: a service "must atomically update the database and send messages in order to avoid data inconsistencies and bugs," yet "it is not viable to use a traditional distributed transaction (2PC) that spans the database and the message broker" [1]. Without it, "if the database update succeeds but the write to Kafka fails, the system ends up in an inconsistent state" [9], and "if one succeeds and the other fails, downstream systems may observe incomplete state" [8]. The pattern fixes atomicity by writing the event to an outbox table in the same local transaction, with a separate relay publishing it later.

The pattern solves the write-side atomicity problem, but it moves the failure surface into the relay, the outbox table, and the delivery semantics. Production experience shows the failures cluster into eight recurring modes.

## 1. Duplicate delivery: at-least-once is a contract, not a bug

Every authoritative description is explicit that the relay produces duplicates. Chris Richardson notes "The Message relay might publish a message more than once. It might, for example, crash after publishing a message but before recording the fact that it has done so" [1]. The Debezium team describes the same window in CDC terms: duplicates arise from "the 'at least once' semantics of this data pipeline," e.g., when "the Debezium connector or the consuming service fail before acknowledging the retrieval of a specific event" [3]. AWS's guidance concurs: "The events processing service might send out duplicate messages or events, so we recommend that you make the consuming service idempotent" [5].

The production failure is not the duplicate itself but the unprepared consumer. The pattern "guarantees at-least-once delivery - not exactly-once," so unprepared downstream processing "risks inconsistent state or triggering actions multiple times (e.g., sending duplicate emails or creating double charges)" [4]. The standard mitigation is an idempotent consumer or inbox table — but that introduces its own operational question: retention. Keeping processed-ID journals "for too long may cause the journal to grow unwieldy, dropping them too early may cause duplicate events to go unnoticed" [2]; Morling recommends a monotonically increasing watermark such as the Postgres LSN instead of UUID journals [2]. Note also a subtlety about broker guarantees: Kafka's "exactly-once" is "exactly-once writes from a producer to a topic partition... It does not guarantee exactly-once processing of the event by the consumer's business logic" [7].

## 2. Ordering violations and silent message loss in polling relays

This is the deepest and least obvious failure mode. Polling-based relays that order by an auto-increment column are broken under concurrency because, in Postgres, sequences backing BIGSERIAL "are evaluated before the transaction commit" [6]. If a later-numbered transaction commits first, "the order in which records were appended to the table may differ from the order of positions," so "we may have messages out of order" and, because rolled-back transactions burn sequence numbers, "we may have gaps in position numbering" [6]. The truly dangerous consequence: "If we optimistically assume that the gaps were caused by rollbacks, we may lose messages" [6] — the relay advances its cursor past rows that had not yet committed. Dudycz concludes that "losing messages is a no-go for most systems" and shows a fix that filters on `pg_snapshot_xmin(pg_current_snapshot())` and transaction IDs; he also warns the "nuke option" of a gapless singleton counter table serializes all writers — "the performance hit... was too big to accept" [6].

Gunnar Morling frames the same problem generally: polling has "poor ordering semantics"; with parallel transactions "it can't be guaranteed that the order of messages in the outbox table... is the same as the order of commits," which "can cause the relay to miss outbox messages, providing consumers with an incomplete feed of events," and "the problem can't be solved generically in the presence of concurrent writers" [2]. His recommendation — and the sources broadly agree — is log-based CDC, where "events are emitted in the exact same order as transactions were committed" [2]. Even then, ordering is only per-key: Debezium uses the aggregate id as the Kafka message key so events for one aggregate go "into the same partition of that topic," letting consumers see them "in the exact order as they were produced" [3]; there is no global order guarantee [7]. AWS adds that broken ordering "might compromise the quality of the data," since you should "Send messages or events in the same order in which the service updates the database" [5]. A related trap on the consumer side: after rebalances and retries, engineers who over-rely on ordering see inconsistency — teams must "design consumers to be tolerant of out-of-order delivery or to explicitly check the event's sequence number/version" [7]. Polling relays that order by timestamp face the further problem of "Clock Skew" across database nodes [7].

## 3. Silent relay failure and unmonitored backlog

Operationally, the most reported production pitfall is "the Silent Failure of the Dispatcher": the relay or CDC connector "can fail silently due to broker connectivity issues, expired credentials, or internal exceptions, yet the application continues to commit events to the Outbox," so "the system can appear healthy while thousands of events pile up" [7]. The outbox is "effectively a queue, and like any queue, it requires monitoring to ensure inflow and outflow stay balanced" [4]; because it lives in the database rather than the broker, "the outbox itself often goes unobserved" while teams watch their Kafka/RabbitMQ dashboards [4]. Minimum telemetry: age of unsent events, inflow rate, outflow rate, relay errors — "when these metrics drift apart... it's a signal that something is wrong, the relay is failing, overloaded, or misconfigured" [4].

## 4. Eventual-consistency lag as a business incident

Even a healthy relay imposes lag, and lag can be exploited. One documented incident: a system deducted an internal currency balance through an outbox pipeline; because processing was delayed, "A user could trigger multiple transactions before the first slow deduction processed - and effectively 'overspend'... this caused a serious incident," and "the backlog built silently" [4]. Sources disagree on how much latency matters: Morling argues the concern is minor — with log-based CDC "changes can be propagated from Postgres to Kafka within a two-digit milliseconds timeframe," and if a few hundred milliseconds of delay breaks a design, "probably there's something not quite right with how the services are cut" [2] — while the incident report above shows that for money-like domains "even short delays can introduce real risk" [4]. Both are right for different domains; the failure is deploying the pattern on a flow that actually required synchronous consistency, where "the Outbox Pattern's inherent latency (eventual consistency) makes it unsuitable" [7].

## 5. Unbounded outbox table growth

"Outbox (and inbox) tables tend to grow silently in the background" [4]. One analysis calls unbounded growth "the most common operational failure": when the cleanup job "is misconfigured, fails, or cannot keep pace with the event volume," index sizes grow, "query times slow down, and the entire database is impacted" [7], hence "Unbounded outbox growth is a common anti-pattern" [7]. In moderate-traffic systems performance "might hold up fine even with hundreds of thousands of records," but it degrades gradually into "subtle but persistent performance issues" [4]. Mitigations: automatic scheduled cleanup [4], avoiding "large blocking deletes" in favor of partitioning or batched retention jobs [8], and — with CDC — deleting the row in the same transaction as the insert, so "the outbox table always is empty" while events are still captured from the transaction log ("it will always be empty" [3]); Postgres users can skip the table entirely via `pg_logical_emit_message()`, which writes only to the WAL [2]. The sources diverge in emphasis here: Morling regards database overhead "mostly as a theoretical concern rather than as an actual, empirically demonstrated problem" [2], whereas the operational write-ups treat cleanup as "not optional; it is a critical, high-priority component" [7].

## 6. Relay scaling failures: co-hosted relays and lock contention

A common architecture mistake is co-hosting the relay inside every API replica. This "works well for small-scale systems with low traffic or a limited number of replicas (typically fewer than five)," but at 10-30 replicas each instance polls "at regular intervals (even a modest 25-50ms)," producing "a storm of database queries" [4]. In one Amazon Aurora deployment, "the database spends considerable CPU time managing locks, not executing queries" [4]. The root cause is "mismatched scaling profiles": API traffic scales with users; the relay scales with write throughput, and "a single relay process instance is enough to handle even high volumes of events" in many systems [4]. Multi-instance relays also require row-locking discipline (`FOR UPDATE SKIP LOCKED` or `READPAST`) so relays "don't block or interfere with each other" [4]; even then, `FOR UPDATE SKIP LOCKED` "can still lead to lock contention and reduced throughput if not carefully managed" [7].

## 7. Batch and crash-recovery edge cases

Mid-batch crashes are safe only if events are marked sent strictly after broker acknowledgment: with SKIP LOCKED semantics "those unprocessed rows will become visible again once the transaction rolls back... nothing gets lost. The downside? Some events might get retried" [4]. Batch sizing is a real tuning failure: too small brings query overhead; "Too large: Increased latency and a higher chance of partial publishes leading to larger retry batches" [7]. Poison messages that repeatedly fail must go to a DLQ because "The Relay must not halt processing of subsequent messages due to a single poison message" [7]. AWS's own polling sample illustrates how easy it is to build an unsafe relay: it batches to SQS then unconditionally deletes (`sqsClient.sendMessageBatch(...)` followed by `outboxRepository.deleteAllInBatch(entities)`), relying on SQS's guarantee that a message "is delivered at least once and doesn't get lost" plus idempotent consumers [5].

## 8. CDC-specific and human failure modes

CDC relays trade polling problems for operational ones: WAL/replication-slot management matters because "If the Relay is down for too long, the log may be truncated, leading to data loss and requiring a full database snapshot and resync" [7]. Finally, the pattern is "potentially error prone since the developer might forget to publish the message/event after updating the database" [1] — an application-level omission no infrastructure catches — and event-design anti-patterns (anemic events forcing synchronous callbacks, or fat events leaking internal schema) reintroduce the coupling the pattern was meant to remove [7]. Backfilling an existing dataset into the outbox under concurrent writes is likewise non-trivial, requiring watermark-based chunked snapshotting to keep log events ahead of backfill events [2].

## Summary

The outbox pattern reliably removes the dual write, but production failures concentrate downstream: duplicates hitting non-idempotent consumers [1][3][5], polling relays that reorder or silently skip committed events [2][6], silently dead dispatchers with unmonitored backlog [4][7], consistency-lag windows exploited as business bugs [4], unbounded table growth [4][7], lock-contention storms from co-hosted relays [4], batch/poison-message mishandling [5][7], and CDC log-retention loss [7]. The consensus mitigation stack: log-based CDC over polling where possible [2], per-aggregate keys for ordering [3], idempotent consumers with watermark dedup [2][8], a separately deployed and monitored relay [4], and automated cleanup treated as a first-class component [7][8]. As Morling puts it: "Friends don't let friends do dual writes" [2] — but adopting the outbox means signing up to operate a second queue that lives inside your database.
