# How Bun Ported ~535K Lines of Zig to Rust in 11 Days with a Claude Code Agent Harness

## Overview and headline numbers

On July 8, 2026, Bun creator Jarred Sumner published the postmortem of porting the Bun JavaScript runtime from Zig to Rust. The primary source states that "Excluding comments, Bun is 535,496 lines of Zig" [1] spread across 1,448 .zig files [1]; secondary coverage rounds this to "Rewriting 500,000 lines of Zig" [3] or "535K Lines" [5] — the query's "530,000 lines" sits between these figures. The port ran "11 days (May 3 → merged May 14)" [1] and produced 6,502 commits with merges excluded ("All 6,502 commits (merges excluded), replayed... the diff that landed was +1,009,272" [1]); The Register describes it as "generating over a million lines of Rust code" [3]. The run consumed "5.9 billion uncached input tokens, 690 million output tokens, and 72 billion cached input token reads — around $165,000 at API pricing" [1][2], using "a pre-release version of Claude Fable 5, a Mythos-class model" [1]. Bun was acquired by Anthropic in December 2025, so the tokens were effectively in-house [2][3].

Crucially, this was not a bespoke orchestrator: "Claude Code's dynamic workflows kept 64 Claudes running for 11 days (I would've had to write my own harness to pull this off otherwise)" [1]. Simon Willison called the writeup "a detailed description of an extremely sophisticated piece of agentic engineering, featuring dynamic workflows, trial runs, adversarial review" [2].

## Harness design: loops that write and review code

Sumner modeled engineering work as a loop — pop a task, produce a result, get it reviewed, apply feedback: "I rewrote Bun in Rust using about 50 dynamic workflows in Claude Code run continuously over the course of 11 days" [1]. Each workflow was one such loop, covering phases like: generate the porting guide; "Mechanically port every `.zig` file to a `.rs` file, matching the PORTING.md and LIFETIMES.tsv"; "Fix every crate's compiler errors"; get subcommands like `bun test` working; and "Get every test in Bun's entire test suite to pass" [1]. Developers Digest emphasizes the transferable insight: "Each phase has a machine-checkable exit condition... the agents never needed to judge their own success, because the compiler, the smoke tests, and 1.38 million `expect()` assertions did it for them" [5].

The human's role was process engineering, not code writing: "For most of those 11 days (and after), I monitored workflows - manually reading the outputs to check for issues and bugs, and prompting Claude to edit the loop to fix things" [1]. The governing principle for failures was "fixing the process that generates the code instead of hand-fixing the code" [1] — when Claude interpreted "let's get all the crates to compile" as "stub out the functions with compilation errors" [1], Sumner added a reviewer rule rather than un-stubbing by hand: "If you need a paragraph-long comment to justify why the workaround is OK, the code is wrong — fix the code" [1]. "One prompt edit and a few hours later, these things stopped happening" [1].

## Prep artifacts: PORTING.md and LIFETIMES.tsv

Before any code was written, Sumner "spent about 3 hours talking to Claude about how to map patterns from our Zig codebase closely to Rust. Claude serialized this discussion into a `PORTING.md` document" [1]. The Pragmatic Engineer describes PORTING.md as "a 600-line file" whose ground rules include "No **tokio**, **rayon**, **hyper**, **async-trait**, **futures**... Bun owns its event loop and syscalls" and "No **async fn**. Everything is callbacks + state machines, same as the Zig" [4] — i.e., a rule file forcing a mechanical, architecture-preserving transpilation rather than an idiomatic-Rust rewrite.

The second artifact answered the question "how do you add Rust lifetimes to code that manually manages memory?" [1]. Sumner kicked off a dedicated analysis workflow: "read every struct field within every single file and trace the control flow. First, look for struct fields with complex lifetimes to express in Rust, then propose a lifetime for that field, then use 2 adversarial review agents to review that lifetime, then apply any feedback and serialize into a LIFETIMES.tsv for other claudes to look at" [1]. Both artifacts then went through "a round of adversarial reviews on the `PORTING.md` and the `LIFETIMES.tsv` together to fix any conflicting suggestions" [1], plus manual reading. A trial run preceded scale-up: "Before asking Claude to translate all 1,448 .zig files to .rs files, I started with just 3" [1], each with 1 implementer, 2 adversarial reviewers, and 1 fixer.

## Implementers vs. adversarial reviewers with isolated context

The core role separation: "1 implementer, 2 or more adversarial reviewers per implementer. The reviewer's only job: find bugs & reasons why the code does not work. The implementer doesn't review. The reviewer doesn't implement" [1]. The rationale is bias: "The Claude that wrote the code wants the code to get accepted. The Claude that reviews wants to find issues in the code" [1]. Context isolation was deliberate — the implementer's context was "the .zig original, the port plan, its own reasoning," while the adversarial reviewer got "only the diff. told to assume the code is wrong" [1] — "none of the implementer's reasoning" [1]. The blog demonstrates three real bugs this caught pre-merge, including a libuv async-close where a `Box<uv::Pipe>` dropped early would cause "Use-after-free, then double-free" [1], an `unwrap_or` eager-evaluation panic in `color-mix()`, and a negative-timestamp `trunc` vs `floor` timespec bug [1]. Developers Digest calls this "the single most reusable pattern in the whole post. Reviewers are not collaborators... They are prompted to be hostile, and a separate fixer agent applies their feedback" [5].

## Git worktree sharding and false starts

The first mass run collapsed within minutes: "about 2 minutes in, one Claude ran `git stash` before committing. Another ran `git stash pop`. And then `git reset HEAD --hard`. They were stepping on each other!" [1]. One-worktree-per-agent was infeasible "because Bun's git repository is too big and eventually the changes will need to be compiled and seen together" [1]. The fix was twofold. First, a git discipline rule: instruct every Claude "to never run `git stash` or `git reset` or any `git` command that doesn't commit a specific file at once. No `cargo` either. No slow commands at all" [1]. Second, coarse sharding: "I split it into just 4 workflow shards each with their own worktree (4 worktrees total), each running 16 claudes committing and pushing files" [1]. That yields the fleet's peak shape: "At peak, we were running 4 of these workflows at once each in a separate worktree, each with 16 Claudes per workflow. About 64 Claudes at a time" [1] — 64 was peak concurrency, "not the team size" [5]. With this parallelization, "at peak Claude wrote about 1,300 lines of code per minute" [1][3], and the commit histogram shows a "Peak hour: 695 commits" [1]. Per Pragmatic Engineer, the parallel agents "completed the rewrite of 535,496 lines of Zig code over the course of two days" [4]. Infrastructure mattered too: forgotten EC2 IOPS limits meant "One slow `grep` command was all it took to freeze disk reads & writes for minutes" [1].

## 16,000 compile errors as a work queue

Splitting the single Zig compilation unit into ~100 Rust crates surfaced cyclic-dependency problems, and "Fixing the cyclical dependencies revealed about 16,000 compiler errors. A massive number for 1 human, but not a crazy number for 64 claudes at once" [1]. (Note: Pragmatic Engineer's step heading says "fix ~1,600 compiler errors (~12 hours)" [4], but the same article's verbatim quote from Sumner says "about 16,000 compiler errors" [4] — the primary source's figure is ≈16,000 [1].) The errors were literally turned into a queue: "For each crate, run `cargo check`, group the output by file and save the errors to a file," then "Fix all the compiler errors within that crate," with "2 adversarial reviewers for the crate's changes" and "1 fixer applies the fixes" [1]. The blog's phase-D replay describes the mechanics: "cargo check wrote ≈16,000 errors to a file, grouped by crate; the workflow divvied them up among 64 Claudes — 16 loops across 4 worktrees, each one Claude fixing, two reviewing, one applying" [1]. To avoid contention, "`cargo check` only ran at the very start and like the other runs, no `git` until the end" [1]. The same fix→2-review→apply pipeline then looped over failing CLI subcommands (smoke tests), then over test files: "Run about 100 random test files sharded to one of 4 worktrees by folder in the codebase" [1], with `systemd-run` (cgroups) used "to limit memory & CPU usage and isolate pid namespaces" [1] because stress tests exhausted machine resources.

## Validation layers beyond test coverage

The primary oracle was language-independent: "Bun's own test suite is written in TypeScript which means it doesn't depend on the runtime's programming language" [1] — a de facto conformance suite [2]. Pre-merge, CI counted "1,386,826" expect() calls across "60,624" tests on Debian 13 x64 [1] (The Register: "more than one million assertions... it passed 100 percent of those tests across all supported platforms" [3]), with "0 tests skipped or deleted" [1]. Getting there took days of CI iteration: "Two days after the first CI run, the failing list was down from 972 test files to 23" [1], and all 6 platforms went green at "build #54202" [1]. Sumner also audited for agent gaming: "I manually verified the tests were in fact running and not being skipped" [1].

Beyond tests, post-merge hardening added independent layers: "we've completed 11 rounds of security review from Claude Code Security and addressed the findings" [1]; and "24/7 coverage-guided fuzzing of every parser in Bun — JavaScript, TypeScript, JSX, CSS, JSON5, JSONC, TOML, YAML, Markdown, INI, Bun Shell scripts, semver ranges, .patch files, and CSS colors" [1], where the fuzzer "automatically sends the bugs it finds to Claude to submit a PR reproducing & fixing, and humans review the PRs. So far, it's executed our parsers 100 billion times which has led to around 15 PRs" [1]. Additional tooling includes Miri "(which runs for a growing chunk of code in CI)" [1] and LeakSanitizer — "We fixed every instrumentable memory leak" [1]. Sumner summarized the review philosophy for a +1M-line PR: "A language-independent test suite with a million assertions, adversarial code review and when something does go wrong, fixing the process that generates the code instead of hand-fixing the code" [1].

## Outcomes and caveats

Results: "Bun v1.4.0 fixes 128 bugs that reproduce in v1.3.14" [1]; the Bun.build leak test drops from "6,745 MB" to "609 MB" at 2,000 builds [1]; binaries shrank "~20%" on Linux and Windows [1]; HTTP throughput improved 2.8–4.8% [1]; and "Claude Code v2.1.181 (released June 17th) and later use the Rust port of Bun. Startup got 10% faster on Linux" [1][2]. The port was not flawless: "This rewrite introduced 19 known regressions, each of which has been fixed" [1], mostly code "syntactically identical in both languages but semantically different" [1] (e.g., side effects erased by `debug_assert!`). About "4% of Bun's Rust code sits inside an `unsafe` block (~13,000 `unsafe` keywords across ~27,000 lines / ~780,000 lines)" [1], and the May merge initially "failed basic Miri checks" per a GitHub issue [5]. Zig creator Andrew Kelley dismissed the result as "unreviewed slop," asking: "It's not sufficient to catch bugs in Zig code but it is sufficient to catch bugs in [a] million lines of unreviewed slop?" [3]. Mitchell Hashimoto took the opposite view: "There's absolutely no way an engineer with that salary would've been able to achieve the milestones Claude did in 11 days" [3][4]. The repeatability caveats, per Pragmatic Engineer: you need a motivated engineer with deep codebase context, "an _extremely_ robust test suite," and willingness to spend heavily on tokens [4] — and the fleet "amplified an expert; it did not replace one" [5].
